# yaPDP Architecture

A high-level map of the codebase. The emulator runs a PDP‑11/70 in the
browser **and** headlessly (pure Node, no DOM). The CPU (`src/pdp11.js`)
executes against a machine that exists in two parallel stacks:

- **Core stack (default)** — the refactored machine layer: core base
  classes (`src/core/`) + one module per device (`src/devices/`), assembled
  by an adapter. `pdp11.html` boots into it unless `?core=0` asks for the
  legacy stack. The same machine assembles in Node via
  `tools/headless-machine.js`.
- **Legacy stack (`?core=0`)** — the monolithic `src/iopage.js`, which owns
  its own copies of every device plus the I/O plumbing, exactly as it did
  before the refactor. Kept as the reference/rollback implementation; the
  e2e parity gate runs every guest on both stacks.

Both stacks expose the same global `iopage` contract (access/poll/reset/
register/scheduleCallback/...), so `src/pdp11-app.js`, the front panel and
every other UI module are stack-agnostic.

The page also answers URL switches besides the stack choice. `?bridge=1`
opens the legacy console-output/tooling surface (see
[machine-layer.md](machine-layer.md)). `?boot=<device>` boots a quick-boot
scenario on load: the key names a scenario in `src/osboot.js`, so the boot
command, the typed steps and the machine profile (console, printer, VT11) come
from there and the caller — the RUN buttons on the landing galleries — carries
nothing but the key. The parameter is consumed once and dropped from the URL, so
the config-driven reload that a profile change triggers resumes through the
pending key instead of booting twice. A key that names no scenario — or a link
that arrived with no key at all (`?boot=`) — boots nothing and shows the same
kind of modal a failed image fetch does (`.modal-box.error`, see
`src/imgerror.js`): the key is named (tamed first: cut by code points, control
characters and bidi overrides replaced), inserted as text rather than markup,
and one button leads to the quick-boot list, so a stale or mistyped link
explains itself instead of looking like a request the emulator ignored. See
[`src/quickboot.js`](../src/quickboot.js).

`?state=<url>` restores a saved machine state on load — the teleport link the
Games tiles and every shared exhibit use. The state is fetched, its images are
identified (and, when the state pins versions, fetched from the media registry),
and only then is CPU/RAM replaced, so a state whose disks do not match is
refused instead of half-applied. The parameter is consumed once and kept in the
address bar only while a device-set reload is in flight, so the reloaded page
applies it once. The restore path lives in [`src/snapshots.js`](../src/snapshots.js);
the URL half in [`src/quickboot.js`](../src/quickboot.js).

The magic-wand dialog has two lists: **Boot** (guest-OS scenarios from
[`src/osboot.js`](../src/osboot.js)) and **Scenario** (pre-built machine states
from `states/`, listed by [`tools/gen-state-manifest.js`](../tools/gen-state-manifest.js)).
The Scenario list is the same restore path as `?state=`, so a state that is not
available offline is refused with a reason rather than a broken machine.

## The machine layer (core stack)

The refactor mirrors the hardware it emulates: devices are *cards* on a
*backplane*, not solder blobs on the CPU. See the
[machine layer deep-dive](machine-layer.md) for the full design, the device
contract, the bridge and the write-back storage split.

## User-facing errors

Most `console.*` output in the emulator is **debug tracing** — CPU/MMU/UDA/disk
traces under `DEBUG_*` flags, NXM reports, "Unknown" terminal escapes, and
informational mount/apply logs. Those stay in the console for developers and are
never shown to the user.

A small set of **user-relevant failures** is surfaced as toasts instead of being
lost in the console. The UI layer (`src/pdp11-app.js`) exposes two hooks:

- `window.__yapdpReportError(text, key)` → `Toasts.show({ category: "error" })`
- `window.__yapdpReportWarning(text, key)` → `Toasts.show({ category: "warning" })`

Modules call these (with a `console` fallback) when a real, user-relevant
failure happens: a bundled image that failed to load (`src/tauri-bundled.js`), a
disk overlay that could not be restored (`src/diskstore.js`), a dropped state
that did not apply (`src/dragdrop.js`), a fullscreen toggle that failed
(`src/fullscreen.js`). The optional `key` feeds the toast subsystem's
deduplication: a repeated identical failure extends one toast instead of
spamming. A missing `Toasts` subsystem is a silent no-op, so the same code path
serves the browser and the Node tests.

### The machine stopped: one published event, one policy

A CPU stop is a **state**, not a log line, so it travels as one structured event
instead of being scraped out of `console.*`:

- the core publishes it from one place — `notifyCpuHalt(reason)` in
  `src/pdp11.js` — which records `CPU.haltReason = { reason, pc, psw, step }` and
  calls the injectable slot `window.__yapdpCpuHaltHook(info)`. There are exactly
  two publishers: the `HALT` instruction and the runaway trap-recursion guard.
  `WAIT` (an idle guest at its prompt) is **not** a stop and never reaches the
  slot, and neither is a panel `STEP` (it says so through `step: true`);
- `CPU.haltReason` is an object on purpose: `captureCPU()` in
  `src/state-format.js` persists only primitives and typed arrays, so the record
  stays runtime-only and the state file format does not change (the `stepActive`
  marker is a non-enumerable property for the same reason);
- `src/halt-notice.js` owns the policy — a `runaway-trap` or a halt at PC ≤ 4
  (trapped into an empty vector) is an `error`, an ordinary guest halt is a
  `warning` with a CONT hint, a STEP halt produces nothing at all, and the dedup
  key `cpu-halt` lets repeated stops extend one toast;
- `src/pdp11-app.js` routes the notice to the toast subsystem and stays silent
  while the quick-boot wizard owns the machine through its input gate (the
  "Take control!" button lives in that toast — preempting it would strand the
  operator). `src/panel-led.js` keeps the reason on the run-state icon as a
  tooltip and repeats the notice on click, so a halt outlives a 4 s toast.

The same event serves the headless test stack: `tests/xxdp-lib.js` reads
`CPU.haltReason` through the sandbox and turns a halted diagnostic into a fast
verdict (`halted at PC 000010`) instead of a budget-sized timeout — see
[xxdp-diagnostics.md](xxdp-diagnostics.md#halt-events-a-stop-is-a-verdict).

**Triggering a stop by hand** (browser console; serve the repo with
`node tools/serve.js`, port 1170). The console must be attached to the document
that runs `pdp11.html`: `CPU` is a `const` and `writePSW()` a function of *that*
document, so on the landing page — which embeds the emulator in an `<iframe>` —
both are undefined. Switch the console's execution context to the `pdp11.html`
frame, or open the page directly:

```js
// an ordinary HALT -> warning: "Machine halted at 001002. Press CONT to continue…"
CPU.mmuMode = 0; CPU.mmuEnable = 0;   // a HALT is a real halt only in kernel, no MMU
CPU.registerVal[7] = 0o1000;          // PC
CPU.memory[0o1000 >> 1] = 0;          // HALT 000000
CPU.runState = 0;                     // STATE_RUN; the CPU loop reschedules itself

// an empty-vector dead end -> error ("…trapped into an empty vector")
CPU.registerVal[7] = 0; CPU.memory[0] = 0; CPU.runState = 0;

// a runaway trap -> error
CPU.trapDepth = 8; trap(0o4, 0);
```

The PC in the notice is the address *after* the fetch (the core increments R7
before dispatch), hence `001002` for a `HALT` deposited at `001000`. The
screenshot `assets/images/manual/dialog-halt-toast.png` is produced from exactly
this path by `node tools/screenshots-manual.js dialog-halt-toast` — a real stop,
not a mocked toast.

## Media files

Disk (`.dsk`), tape (`.tap`), and paper tape (`.ptap`) images live in the [`media/`](../media/) directory. Many are ZST‑compressed to stay within GitHub size limits. Disk and tape images ship as `.zst` and are fetched and decompressed in the browser via the bundled fzstd library (no raw `.dsk`/`.tap` copy is required). See [`media/README.md`](../media/README.md) for the naming convention.

### Replacing an image invalidates the caches and snapshots by itself

Three things remember something about a disk image and must not be trusted
once the image changes:

| Remembers                        | Where                        | Tagged with                                         |
| -------------------------------- | ---------------------------- | --------------------------------------------------- |
| guest writes (write-back blocks) | IndexedDB, `yapdp-diskstore` | the identity of the image they were written to      |
| a snapshot's disk overlay        | inside the snapshot record   | the identity, per image url                         |
| the whole snapshot               | IndexedDB, `yapdp-snapshots` | `imageFingerprints`: url → identity at capture time |

All three carry `src/imagefingerprint.js`'s SHA-256 of the **decompressed**
image bytes (64 hex digits), recorded by the fetch path when the bytes actually
arrive (`DiskStore.registerImage`). Compression is a transport detail: a
recompressed image keeps its identity, while replaced content changes it. The
same digest is what the versioned registry publishes
([image-registry.md](image-registry.md)), so a snapshot can pin an exact
version instead of relying on the file name. Nothing has to be bumped by hand:
replace `media/rk0.dsk.zst` and every identity derived from it changes, so

* a cached block saved from the previous build no longer matches and is
  ignored (`DiskStore.getBlock`), and an overlay recorded against it is skipped
  (`DiskStore.restoreOverlay`) — instead of being written over a different disk;
* `SnapshotStore.restore()` refuses the snapshot before it touches CPU or RAM,
  explains why in a dialog and offers to delete it. A half-applied restore
  (saved memory on top of a disk it does not match) is worse than none.

**Unknown never invalidates.** An identity that was never computed — a page
opened as `file://`, a desktop-bundle image, any host where the image was not
fetched — is `null`, and `null` matches everything (see
`ImageFingerprint.matches`). This is what keeps those deployments working
exactly as before, and it is pinned by tests.

This replaced the old hand-maintained `IMAGE_VERSION` constant, which was
forgotten in practice: `rp1.dsk.zst` (BSD 2.11) was repacked three times while
the version stayed `0.1.0`, so a stale block matched and was overlaid onto the
new disk. The short FNV-1a/32 identity that followed it is legacy now: readers
still accept it where it appears, and `tools/convert-state-format.js` rewrites
it to SHA-256 (refusing when the original bytes cannot be verified).

### Drive bindings travel with the state

The Storage page can bind any drive to any mounted image
([`src/mountmap.js`](../src/mountmap.js)); the controllers resolve their url
through that table. A state records the table as its `mountmap` manifest field
(`{ "rk4": "rk5.dsk" }`), so a state taken on a remapped drive restores the same
way on a machine that never made that binding — and `device` names the DRIVE
(`rk4`), not the image file.

Restore order for that field:

1. the preflight (`incompatibleImages`) still runs first — a refused state must
   not damage the bindings the user made locally;
2. a state with the field REPLACES the local table (`{}` included); a legacy
   state without it leaves the local table untouched;
3. the table is persisted to `localStorage`, so a Reboot or a power cycle reads
   the same image;
4. every bound url gets a drive provider, so a remapped drive that is not in
   `mounted` does not read zeroes;
5. `restoreDevices` runs afterwards, and each disk controller drops its control
   blocks in `restore()` — a control block caches the url resolved when it was
   created and is never serialised in a state.
