# Publishing the demo videos to YouTube

The promo clips assembled by [`tools/assemble-video.js`](../tools/assemble-video.js)
(`video/<clip>.mp4` with their `.srt` and `.chapters.txt` sidecars) can be
published to the project's YouTube playlist **in one command**:

```
npm run youtube:publish                    # the featured set (see below)
npm run youtube:publish -- --all           # every clip in the manifest
npm run youtube:publish -- rt11 xxdp       # a hand-picked list
npm run youtube:publish -- video/          # a directory (or single files)
npm run youtube:publish -- --dry-run --all # preview the plan, send nothing
```

`npm run youtube-public` is an alias for `npm run youtube:publish`.

For each video the publisher sets the title, a description (see
[What gets published](#what-gets-published)), attaches the `.srt` as captions
and appends the video to the configured playlist. It is **idempotent**: what has
already been uploaded is remembered in `video/youtube-state.json`, so re-running
skips finished videos and only completes what is missing.

```
tools/youtube-publish.js   CLI + YouTube Data API v3 calls (network shell)
tools/youtube-util.js      all decision logic (pure, unit-tested)
tools/youtube-meta.json    playlist id, defaults, featured list, overrides
video/youtube-manifest.json  generated by `npm run video:demo`
video/youtube-state.json     generated: video ids + sidecar progress
```

## 1. One-time setup: OAuth desktop client

Uploading needs user consent — an API key is not enough.

1. In the [Google Cloud console](https://console.cloud.google.com/) create (or
   pick) a project and **enable the YouTube Data API v3**
   (APIs & Services → Library).
2. Configure the OAuth consent screen (External, "Testing" is fine for a single
   account; add your own Google account as a **test user**).
3. Credentials → **Create credentials → OAuth client ID → Desktop app**.
4. Download the JSON and save it in the repository root as
   `.youtube-client.json` (gitignored). The flat
   `{"clientId":…,"clientSecret":…}` shape works too; on CI use the
   `YT_CLIENT_ID` / `YT_CLIENT_SECRET` environment variables instead.

## 2. Authorise once

```
npm run youtube:auth
```

The tool prints a consent URL, waits on `http://127.0.0.1:8765/oauth2callback`
and stores the **refresh token** in `.youtube-token.json` (gitignored, mode
0600). The client secret is never stored. Use `--port` if 8765 is taken.

Verify:

```
npm run youtube:publish -- --whoami
```

## 3. Find and configure the playlist

```
npm run youtube:publish -- --list-playlists
```

prints every playlist of the channel (`id`, number of videos, title). Paste the
wanted id (or any `…/playlist?list=…` URL) into
[`tools/youtube-meta.json`](../tools/youtube-meta.json) and list the clips that
`npm run youtube:publish` should publish by default:

```json
{
  "playlistId": "PL…",
  "defaults": { "privacy": "unlisted", "captions": true, "captionLanguage": "en" },
  "links": { "repo": "", "site": "" },
  "hashtags": ["#PDP11", "#retrocomputing"],
  "featured": ["rt11", "xxdp", "basic"],
  "reel": { "slug": "yaPDP-demo", "title": "…", "description": "…" },
  "overrides": { "rt11": { "description": "…", "tags": ["RT-11"] } }
}
```

`featured` is the default set — `npm run youtube:publish` never publishes
anything else unless `--all` (every clip) or explicit clip names/`--reel` are
given. A truncated or mistyped playlist id is rejected instead of being sent.
Per-clip titles/descriptions/tags come from the generated manifest (see below)
and can be overridden per slug via `overrides`.

## 4. Keep the manifest fresh

`video/youtube-manifest.json` (titles, descriptions, tags, sidecar paths,
durations) is written by the assembler, so the usual cycle is:

```
npm run record:video     # record the clips
npm run video:demo       # assemble reel + per-clip MP4s + the manifest
npm run youtube:publish -- --dry-run --all
```

If the manifest is missing the publisher falls back to scanning `video/` for
`*.mp4` and uses the overrides/defaults from `tools/youtube-meta.json`.

## What gets published

* **Description** — the clip summary from the manifest, then the chapter block
  from `<clip>.chapters.txt`, then the project links, then the hashtags.
* **Chapters** — YouTube reads chapter markers from the description timestamps.
  They are only rendered when the first one is `0:00`, there are at least three
  and each lasts ≥ 10 s, so the publisher clamps the first mark to `0:00` (the
  intro card), drops too-close followers and **omits the whole block** when it
  cannot be made valid.
* **Captions** — `<clip>.srt` is uploaded with `captions.insert`
  (`--no-captions` skips it).
* **Playlist** — `playlistItems.insert` (`--no-playlist` skips it; the video is
  uploaded either way).

## Quota: why "everything" runs in batches

The YouTube Data API grants **10 000 units per day**:

| Call | Units |
|------|-------|
| `videos.insert` | 1 600 |
| `captions.insert` | 400 |
| `playlistItems.insert` | 50 |

One fully published video therefore costs **2 050 units** — about five videos
per day. The publisher plans a batch accordingly:

```
npm run youtube:publish -- --all --limit 4        # at most 4 uploads now
npm run youtube:publish -- --all --budget 8000    # or by unit budget
npm run youtube:publish -- --all --resume         # continue the next day
```

A `quotaExceeded` response stops the run cleanly (exit code 0) and prints what
is left; `video/youtube-state.json` already records everything that succeeded,
so the next run continues without re-uploading. `--force` re-uploads a video
whose local MP4 changed (it creates a **new** video id; the old one stays in the
channel until deleted by hand).

## Publishing from CI (optional)

`.github/workflows/videos.yml` builds the clips as a downloadable artifact.
Because the daily quota is so small, publishing stays a deliberate, local step;
if you do want it in Actions, add the secrets `YT_CLIENT_ID`,
`YT_CLIENT_SECRET` and `YT_REFRESH_TOKEN` (or `YT_ACCESS_TOKEN`) and run:

```
node tools/youtube-publish.js --all --dry-run     # default: plan only
node tools/youtube-publish.js --all --limit 4     # then actually publish
```

The endpoint overrides `YT_API_BASE` / `YT_UPLOAD_BASE` / `YT_OAUTH_BASE` /
`YT_AUTH_BASE` and the workspace overrides `YT_VIDEO_DIR` / `YT_META_FILE` /
`YT_STATE_FILE` / `YT_MANIFEST_FILE` exist so the pipeline can be driven against
a stub service — that is exactly what
[`tests/youtube-publish.test.js`](../tests/youtube-publish.test.js) does.

## Troubleshooting

| Symptom | Cause / fix |
|---------|-------------|
| `Not authorised — run npm run youtube:auth` | no/expired refresh token; re-run `--auth` |
| `invalid_grant` after the refresh | consent revoked, or the clock is far off; re-run `--auth` |
| Google returns no refresh token | access was already granted without `prompt=consent`; revoke at <https://myaccount.google.com/permissions> and retry |
| `Playlist ID looks invalid` | a truncated id (e.g. `PLbR5Jg6Ojbn0`) — copy it from `--list-playlists` |
| Chapters not shown on YouTube | fewer than three marks, a chapter shorter than 10 s, or the first one not at `0:00`; the block is dropped as a whole |
| `Quota exceeded` | expected after ~5 uploads; re-run with `--resume` after the quota resets (UTC midnight) |
| `403 forbidden` on upload | the OAuth client's project does not have the YouTube Data API enabled, or the channel is not verified for long videos |
| Nothing is published | `featured` is empty and no selector was given — pass `--all` or clip names |
